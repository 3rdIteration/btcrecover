# Blockchain.com v5 wallet encryption

The v5 main-password format was investigated from the JavaScript served by the
[official login page](https://login.blockchain.com/auth/login) on 1 November 2026.
An independent wallet made with the official tooling is included as
[`blockchain-v5.0-official-wallet.aes.json`](../btcrecover/test/test-wallets/blockchain-v5.0-official-wallet.aes.json).
Its test password is `BTCR-test-passw0rd`. Its expected BIP39 mnemonic is:

```text
omit lawn check broccoli resemble hover bonus glide security call oak benefit
```

This is a public test wallet. The fixture preserves the client's original
ciphertext and 300,000-iteration setting; it was not generated by BTCRecover.

## Encryption layout

The JSON wrapper contains:

```json
{
  "version": 5,
  "algorithm": "sha256",
  "pbkdf2_iterations": 300000,
  "payload": "<base64-encoded IV and ciphertext>"
}
```

Decode `payload` from base64, then split off the first 16 bytes. Those bytes are
both the PBKDF2 salt and the AES-CBC IV. Derive the 32-byte AES key as:

```python
key = hashlib.pbkdf2_hmac(
    "sha256", password.encode("utf-8"), iv, pbkdf2_iterations, dklen=32
)
```

Decrypt the remaining bytes with AES-256-CBC. The final plaintext byte gives the
padding length, which must be between 1 and 16; remove that many bytes and parse
the remaining UTF-8 JSON. This is compatible with the legacy ISO10126 unpadding
used by BTCRecover. The investigation did not independently establish whether
the new client fills the other padding bytes randomly or repeats the length;
both conventions use the same final length byte.

The important change from v4 is PBKDF2-HMAC-SHA256 instead of HMAC-SHA1. Increasing
the accepted version alone cannot recover this fixture. Use the wrapper's
`algorithm` and iteration count; do not infer the PRF from the version or hardcode
the observed migration limits. When `algorithm` is absent or empty, BTCRecover
uses the legacy SHA1 fallback. Unknown algorithms are rejected explicitly.

## Repeating the JavaScript investigation

1. Open the login page in a browser and open Developer Tools. In Network, filter
   for JavaScript and reload. Search all loaded Sources, including lazily loaded
   chunks. The deployment examined here used Next.js/Turbopack chunks under
   `/_next/static/chunks/`. Chunk names and module numbers change on deployment.
2. Search for `V5_MIGRATION`, `hashingAlgorithm`, `minPbkdf2` and `maxPbkdf2`.
   The configuration observed with migration enabled was version 5, SHA256,
   minimum 300,000 and maximum 600,000 iterations. With migration disabled it
   selected version 4, an undefined hashing algorithm, and 5,000–20,000 iterations.
   These are client configuration values, not parser acceptance rules.
3. Find the migration predicate. It checks the stored payload version, algorithm
   and iteration count against that configuration. This connects the feature
   flag to the on-disk wrapper, rather than merely to a UI label.
4. Follow the wallet creation and save functions to their encryption helper.
   In the observed bundle the helper was called with the wallet JSON, password,
   iterations, version and hashing algorithm. Track the corresponding decrypt
   arguments from `payload`, `pbkdf2_iterations` and `algorithm` as well.
5. Follow imports into the crypto helper. Search for `pbkdf2`, `pbkdf2Sync`,
   `createDecipheriv`, `aes-256-cbc`, base64 decoding and 16-byte slices. Establish
   which value becomes the PBKDF2 digest, salt, key length and AES IV. Do not treat
   an occurrence inside a generic crypto polyfill as proof that the wallet uses
   it. The polyfill's default digest was SHA1; the v5 call sites supply SHA256.
6. Validate the inferred scheme with an independently created wallet and a known
   password. Verify the entire decrypted JSON and a known seed or derived key,
   rather than only matching a plausible first plaintext block. The regression
   test checks the fixture's BIP39 mnemonic and exported account private keys.

For locating the historical code, `0g74adnuzga7o.js` contained the version config
(module `620947`) and wallet creation calls; `2ojijw8y7gg6s.js` contained migration
logic; `362x3rupuessk.js` contained save/encrypt call sites; and
`1ruuqi91dkc67.js` contained crypto polyfills. These names are investigation
breadcrumbs, not stable API identifiers. The call-site inspection supported the
SHA256 hypothesis; successful decryption of the independent fixture established
the actual key derivation and IV layout.

## BTCRecover paths and validation

`WalletBlockchain` carries the parsed PRF through CPU verification, full wallet
decryption and the OpenCL PBKDF2 context. `WalletBlockchainSecondpass` uses that
PRF when decrypting the outer wallet; the second-password hash scheme is unchanged.

`extract-blockchain-main-data.py` preserves legacy `bk:` extracts. A SHA256
extract adds byte `0x01` after the existing ciphertext block, IV and little-endian
iteration count, before the CRC. Its payload is 37 bytes instead of 36. Older
BTCRecover releases cannot consume the extended extract.

Run the v5 regression tests, including GPU verification when available:

```console
python -m unittest btcrecover.test.test_passwords.TestBlockchainV5 -v
```

Run the required complete suite:

```console
python run-all-tests.py --no-pause
```

When the GPU is occupied, set `BTCRECOVER_SKIP_GPU_TESTS=1` before running the
suite (PowerShell: `$env:BTCRECOVER_SKIP_GPU_TESTS = '1'`). Remove that variable
on the GPU test PC (`Remove-Item Env:BTCRECOVER_SKIP_GPU_TESTS` if set), then run
the v5 tests again. OpenCL selects the existing SHA256 PBKDF2 kernel; hardware
correctness and performance still need validation on an available GPU.
